#### A-3. outbox 租约模型无 fencing token + 固定 10min 租约 —— 架构头号问题 🟢 `(High，MySQL+worker 两 agent 收敛 + Codex 三方收敛，已核实)`
- `complete()`（`mysql.rs:1973`）与 `fail()` 重试分支（`mysql.rs:2035`）**无条件按 id 改状态**，无 `AND status='processing'`、无租约/版本校验（仅 dead 分支有 `AND status<>'dead'`）。`fail()` 还是非事务 SELECT-then-UPDATE。
- 租约硬编码 `INTERVAL 10 MINUTE`（`mysql.rs:1927`），无续租；最坏任务时长会超过它：ChunkSync 多批 ×4 重试 ×（60s 超时+≤60s Retry-After）≈ 8min+；DirSummarySync 两次串行 LLM ≈ 16min。
- 后果链：慢任务超租约 → 被另一 worker 重复 claim（retry_count+1）→ 重复 embedding/LLM 开销、放大 429 雪崩；**更糟**：同文件两 executor 读了 v1/v2 内容、按 pk 交错写 Milvus + 各写 watermark → **Milvus 留 v1/v2 混合 chunk 但 watermark 谎称已干净**，reconciler 查不出；健康但慢的任务因租约过期累计 retry 被误判 dead-letter。
- 修复：地板 = `complete`/`fail` 都加 `WHERE id=? AND status='processing'`;真解 = lease/fencing token 列 + 心跳续租。

#### A-4. outbox 毒丸：一条无法解码的行卡死整个异步队列 `(High，机制 certain；触发 中等，已核实)`
- `claim()` 里 `let evt = row_to_outbox(r)?;`（`mysql.rs:1914`）的 `?` 让整个事务回滚；`ORDER BY id ASC` 让同一坏行每轮最先被选 → chunk sync / summary / 向量写**全停**，无 skip/dead-letter 兜底。
- 触发：发新 `OutboxEventType` 变体后回滚旧二进制，或手改行。修复：解码失败标 dead 并 continue。

### 🟢 P2 — 可延后 / 文档化

- **FUSE writeback（opt-in，非默认）两处数据损坏**：并发写撞 in-flight PUT 致 `base_rev` 卡旧、之后所有保存静默丢失（H-1）;>10MB per-file cap 降级路径写零填充前缀**腐化文件**（H-2）。推 writeback 为默认前必修。
- **reconciler 在 >16383 行的 workspace 直接 500** 🟢（Milvus A8 + worker F8 收敛）：唯一漂移修复工具在"大到值得修"的 workspace 上不可用。需 pk-cursor 翻页替代 offset。
- **空文件在 reconciler 里永远报 phantom `chunk_missing`**：dry-run 永不收敛 clean，`dry_run=false` 反复入队空 re-embed。
- **优雅关闭在 await 点直接砍在飞任务**：不 `fail()`、不释放租约，部署重启让任务空烧 retry，连续两次部署可误 dead-letter。
- **文件级摘要防抖是死代码**（`worker.rs:344` `#[allow(dead_code)]`，已核实）：空闲 worker 下每次保存触发整条 L0+L1 + 目录聚合 LLM 链。
- **web 控制台把 `vk_` 存 localStorage + `marked` 未消毒**（`main.ts:873`）：当前 docs 同源可信不可利用，但 `vk_` 是最高权限凭证 + 未消毒 innerHTML 是潜在 XSS 接管面。
- **读路径 Milvus 全程 `consistencyLevel: Strong`**：支撑 read-your-writes，但把租户读延迟耦合到全局写 backlog，任一租户 bulk-load 时 search p99 会尖。可考虑 search 走 Bounded、仅 query 保 Strong。
- **无 CHARSET/COLLATION 声明**：MySQL8 默认 `_ci`，`/A.txt` 与 `/a.txt` 各自能插但查询/删除会撞;path 列建议显式 `utf8mb4_bin`。

### 架构瓶颈总结（非 bug）
1. **outbox 租约无 ownership 概念**（A-3）—— 异步层结构性弱点，fencing token + 心跳一次解掉一族。
2. **reconciler 16384 行天花板** —— 公司级规模能力悬崖。
3. **每请求时长 = 上游超时之和**，而非 server deadline —— p99 跟上游抖的真因。
4. **embedding 是读写吞吐天花板** —— 已有方案（`embedding-throughput-plan.md`，先上线后做），与 A-3 租约问题互相放大。

### A. 架构瓶颈与可扩展性

**B-A1. 向量数据面每个请求都强依赖 MySQL 控制面热路径** — `auth.rs:165-187`, `vectors.rs:239-253`, `mysql.rs:2705-2724`, `mysql.rs:2645-2660`, `config.rs:34-49` — 严重度 HIGH / 置信度 HIGH
`/v1/vectors/{upsert,search,query,delete}` 先经 `AuthDbWorkspace`，每次 bearer 都调 `get_workspace_key_by_hash` 查 MySQL;handler 随后又调 `resolve_dataset` 查 active dataset。MySQL pool 默认 `max_connections=50`，高 QPS 下数据面先耗尽控制面连接池，向量请求在到 Milvus 前阻塞/超时。这是所有 vectors 请求的无条件路径，数据面吞吐被 MySQL pool 直接限流。

> **2026-06-11 生产压测证伪，关闭**：.161 外压 .85，query 5,650 QPS 时框架+MySQL 层 0.4ms、
> 连接池峰值 10/50。`6e6d4bf` 单查询鉴权后两跳 MySQL 不构成瓶颈，无需缓存/扩池。
> 见 `docs/archive/loadtest-prod-2026-06-11.md`。

**B-A2. 按需 reconcile 对大 workspace 是全量 Milvus 扫描 + client 端去重** — `reconcile.rs:52-55`, `reconciler.rs:273-283`, `reconciler.rs:404-414`, `milvus.rs:1304-1335`, `milvus.rs:1337-1366` — MEDIUM / HIGH
server 拉 MySQL 全量 file/summary id，再用 Milvus `entities/query` 按 `limit=16383 + offset` 扫 workspace 下全部 chunk/summary，最后在进程内建 `HashSet` diff。大 workspace 把 reconcile 变成 O(全量向量行数) 的 Milvus 扫描 + server 内存压力，随规模线性放大。

**B-A3. FUSE writeback 单文件超限会 drain 全局 commit queue，造成跨文件队头阻塞** — `fs.rs:620-635`, `fs.rs:1561-1574`, `commit_queue.rs:167-170`, `commit_queue.rs:203-219` — MEDIUM / HIGH
文件写超 per-file cap 后进 `sync_flush_and_evict_shadow`;注释说 drain "this path"，实际调 `q.drain()` → worker `drain_all` 同步 fire 所有 pending path 的 PUT。一个大/慢文件的 fallback 阻塞其他无关文件的前台 write，放大 FUSE 写延迟尾部。

### B. 实现真 Bug

**B-B1. `/v1/apps/{app_id}` 控制面在 veda-server 内无任何鉴权且默认挂载** — `apps.rs:1-7,34-44,104-113,119-150,156-174`, `mod.rs:31-49`, `main.rs:325-333` — **CRITICAL** / HIGH
router 总是 merge `apps::routes()`;handlers 无 `AuthAccount`/`AuthWorkspace`/metrics token/任何 header gate。直达 veda-server 的请求可直接 `POST /v1/apps/{app_id}/workspaces` 自动开户建 workspace、`GET` 枚举、`DELETE` 软删。同一生产二进制里存在可变更控制面的无凭证入口，安全性完全依赖进程外网关隔离。

**B-B2. Outbox lease 过期后旧 worker 仍可无条件改写新 owner 的任务状态** — `mysql.rs:1894-1946,1973-1981,1984-2047`, `worker.rs:77-120,167-197,239-333,395-445` — HIGH / HIGH
worker A claim task，lease 固定 10 分钟;ChunkSync/SummarySync 可跑外部 embedding/LLM/Milvus。lease 过期后 worker B 重新 claim 同一 row;A 后续 `complete(task.id)` 按 id 无条件置 completed，或 `fail(task.id)` 按 id 无条件置 pending/dead。旧执行者覆盖新执行者状态 → 重复处理、完成任务被复活、或错误 dead-letter。SQL 更新无 owner/fencing/status 条件，且 handler 确实含可能超 lease 的外部调用。

**B-B3. 匿名开户返回的 bundled `wk_` key 无法通过鉴权** — `account.rs:236-263`, `mysql.rs:545-572,2295-2306,2705-2724` — HIGH / HIGH
anonymous route 构造 `WorkspaceKey { account_id, kind }` 并把明文 `workspace_key` 返回;但 `create_anonymous_bundle` insert 时遗漏 `account_id`、`kind` 列 → 默认 `account_id=''`，backfill 只在 migrate 时跑。后续 wk 鉴权 `INNER JOIN veda_accounts a ON a.id = k.account_id` 查不到账号 → 直接 401。返回给用户的一次性 credential 在主鉴权 SQL 下必然不匹配。

**B-B4. FUSE writeback unmount 时 PUT 失败被吞，脏数据随进程退出丢失** — `fs.rs:1978-2009`, `commit_queue.rs:167-170,237-251`, `shadow.rs:8-10` — MEDIUM / HIGH
`destroy()` touch 所有 Dirty/LocalOnly 后 `q.drain()`;commit worker `fire()` 遇 `client.write_file` error 只 `warn!` 并留 entry Dirty;`Drain` 仍 ack，`destroy()` 继续返回。shadow 是内存态，进程退出后这批 Dirty bytes 无持久副本。正常 unmount 路径里服务端 PUT 失败没传回 FUSE，用户以为卸载完成但数据未落远端。

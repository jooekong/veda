# Agent / 团队记忆（设计提案）

> **状态：提案，未排期，一行代码没写。** 2026-08-07 业界调研 + 方案初稿；2026-08-11 二轮对标核查
> （§17 增补）+ Claude/Codex 双评审后修订，并落三项拍板：**记忆可编辑（零状态机）、
> 团队域无审批（wiki 式轻治理）、principal 只做归属标识（不新增鉴权）**。
> 文中所有能力都是「打算做」，不是「已经有」。

---

## 1. 一句话说清楚这是什么

veda 现在存的是**文档**：你传一个文件进来，它切块、做摘要、能搜、能问答。

这个提案是让 veda 再存一类东西：**记忆**——一句话一条的事实，比如

- 「集成测试必须加 `--test-threads=1`」
- 「生产节点 .85 上没有 mysql 客户端，操作要从 Mac 走 SSH 隧道」
- 「Joe 偏好最简方案，复杂优化要有证据才上」

这些东西不适合当文件传（太碎、随时变、经常是某个人某次踩坑得来的），但恰恰是 agent 每次开工最需要先知道的。

同时要分清两种记忆：**个人的**（我自己的笔记和偏好）和**团队的**（写给全队看的事实）。
两者要能并存，互不污染，个人觉得值得共享的东西可以直接写进团队域。

---

## 2. 为什么值得做

三条理由：

1. **现有底座基本够用**。要用的东西 veda 都有了：多租户、混合检索、embedding/LLM 管线、
   后台任务（outbox）、MCP 接入面、管理后台。记忆本质上是「带归属的小文档」，
   编辑后重嵌入直接复用文件那套 update→re-embed 的既有管线。新写的代码主要是两张表、
   一个 service、几个工具、一条后台任务。
2. **记忆和证据在同一个库里**——这是别人给不了的。团队记忆可以直接指向同 workspace 的文档、
   qa_log 记录；`/v1/answer` 回答问题时可以同时用「文档说了什么」和「团队记过什么」，
   两边互相印证。mem0、Letta、Zep 都是纯记忆系统，证据在别的地方。
3. **团队记忆业界做得薄，veda 走轻治理路线**（详见 §17 调研）。业界的团队记忆要么没有共享域，
   要么共享了没治理——GateMem 基准实测现有系统越权泄露率 8.9%–33.9%、删除后仍能答出率
   2.3%–37.2%（它们靠 LLM 自律和排序软过滤）。veda 不走审批仪式，走 **wiki 式轻治理**：
   署名 + 人人可改可删 + 硬删彻底传播，配物理分域，目标是把 GateMem 那两个指标做成
   **确定性归零**（SQL 过滤 + 真删行，集成测试可以直接断言）。

## 3. 三层结构，和文档那套不是一回事

记忆分三层。**注意不要用 L0/L1/L2 命名**——文档那套是「摘要在上、原文在下」，
记忆这边正好反过来（原始对话在下、摘要在上），同名反向会把人搞晕。就叫这三个名字：

| 层 | 是什么 | 例子 | 特点 |
|---|---|---|---|
| `episodes` | 原始对话/会话记录 | 企微群里的一次问答、一段 coding 会话 | 只追加不改，不进日常检索，只用来溯源 |
| `memories` | **原子记忆**（一条一个事实） | 「集成测试要加 --test-threads=1」 | 检索主力，本方案的核心，**可编辑可删除** |
| `digest` | 编译出来的视图 | 「testing 主题块」「张三的偏好画像」 | 派生产物，丢了能从原子层重建 |

原子记忆有两个来源：

- **agent 主动写**（第一阶段只做这个）：agent 觉得某件事值得记，直接调工具存一条
- **从对话里自动抽**（第三阶段）：后台任务读 episodes，用 LLM 抽出原子事实

## 4. 个人和团队怎么分

### 4.1 分在存储位置上，不是分在一个标记位上

早期想法是一张表加一个 `visibility` 列（private/team），靠查询条件过滤。**这个方案被否了。**

原因很实际：那意味着同事的私密笔记和团队记忆躺在同一个查询范围里，
每一条业务 SQL 都要记得多写一个可见性条件。GateMem 测试专门测过这个，
现有记忆系统在多人共享场景下普遍会把越权内容和已删内容检出来。

改成**归属分域**：

```
每条记忆有一个归属 = (scope_type, scope_id)

团队记忆 → (workspace, W)     存在团队域里
个人记忆 → (principal, P)     存在个人域里，压根不在 W 的范围内
```

说穿了，这和 veda 现有的 workspace 隔离是**同一根过滤列、同一套机制**——不是物理隔离，
强度来自两条纪律：

1. **所有记忆读取必须经由唯一一个带 scope 过滤的查询原语**，不允许任何旁路查询直接摸表
2. **P 永远由服务端从请求身份解析**（网关用户 / 企微 userid / key），不接受客户端入参指定

配套把 GateMem 的两个治理指标写成集成测试断言：别人的个人域内容检出 = 0、已删内容检出 = 0。
这是确定性行为，不是概率承诺。

工程上不会爆炸：记忆用**一个共享的 Milvus collection + scope 列过滤**
（学 fs workspace 的做法，不是 db workspace 那种一个 workspace 一个 collection）。
几千个员工就是几千个 scope 值，不是几千个 collection。

### 4.2 个人记忆还要再切一刀

「个人记忆」其实是两种东西，混在一起会串味：

- **随身偏好**：「Joe 喜欢中文回复」「偏好最简方案」——跟着人走，在哪个项目都该生效
- **项目内私人笔记**：「这个 repo 测试要单线程」「.85 的 MySQL 走隧道」——只在那个项目有意义，
  带到别的项目是噪音，甚至是信息泄露

实现只需要一根列：个人域的记忆带 `origin_workspace_id`。
项目笔记带上它，随身偏好留空。

这和 Claude Code 的 `~/.claude`（全局）+ 项目内记忆是同一个结构，
ChatGPT 的 user memory × project 也是这么切的——行业在这一刀上完全一致。

## 5. 「人」是归属标识，不是权限系统

veda 现在有租户（Account→Workspace），但没有「人」。principal 的目的是**标识记忆属于谁**：
个人域的 scope、每条记忆的署名、画像的归属。鉴权是附带的，而且**刻意不新增**：

- 数据面照旧：`wk_` key 定 workspace，平台面走既有外部 authz，记忆不引入新的权限动作
- 个人域的私密性 = 上面 §4.1 的第二条纪律（P 从身份解析），这是 API 形状，不是权限系统
- admin 面 = 既有 `VEDA_ADMIN_TOKEN`，记忆多一块浏览/编辑/删除的面板

要加的表就一张，最小：

```sql
veda_principals (
  id, kind ('human' | 'agent'),
  source ('gateway' | 'wecom' | 'key'),
  external_id, display_name
)
```

第一次见到就自动建一条（和现在 `ensure_account` 自动开户一个套路）。

身份从哪来——三个现成的来源，都已经在跑：

| 接入面 | 身份来源 | 可靠程度 |
|---|---|---|
| 平台网关面 | `GatewayUser`（平台鉴权背书） | 权威 |
| tunnel（企微） | 提问人 user_id（企微背书） | 权威 |
| 原生 `wk_` / MCP | **key 就是身份**（一人一把 key，或一个 agent 一把） | 够用 |

第三行要说明白：原生面没有登录态，所以「一把 key = 一个身份」，
**共享 key 就等于共享记忆**——既共享可见性，也共享写入权（一个人被 prompt 注入，
污染的是整把 key 的记忆域，见 §13 的赌注）。想让 MCP 下的每个人有自己的私密记忆？
给每人发一把 `wk_` 就行，key 的增删改查是现成的。

**明确不做的三样**：

- **成员管理**（谁能进哪个 workspace）：平台鉴权已经外置了，平台就是成员系统；
  原生面 key 表挂个 principal 标签就是轻量成员表。veda 自己再建一套账号权限体系是最大的过度设计
- **key 轮换/迁移机制**：换 key 想保留个人域，把新 key 的 principal 标签手工挂到旧 principal
  上即可，不做产品化流程
- **account 级租户边界**：单公司部署，网关/企微身份全司唯一，同一个人在两个业务方
  (Account) 下合并成同一个 principal，**恰恰是随身偏好想要的效果**。真做对外多租户时
  再给 principals 加一列 account_id 进唯一键（无向后兼容包袱）

## 6. 数据模型

两张新表，**零状态列**。所有关系都做成**行上的列**，不建关系表、不建边表——关系表是通往图数据库的第一步，veda 不迈。

```sql
-- 原子记忆
veda_memories (
  id,
  scope_type,               -- 'workspace' | 'principal'
  scope_id,
  origin_workspace_id,      -- 个人域用：项目笔记带上，随身偏好留空
  topic,                    -- 主题，相当于记忆的「目录」，见 §7
  kind,                     -- 'fact'|'preference'|'decision'|'procedure'|'derived'
  content,
  content_hash,             -- UNIQUE(scope_type, scope_id, content_hash)：
                            -- 去重压到 DB 层，并发写同一事实天然挡住
  source_ref JSON,          -- 证据来源：文件路径 / qa_log id / episode id；
                            -- derived 记忆存支撑它的那批记忆 id
  expires_at,               -- 可空，写入时就知道保质期的才填
  last_used_at,             -- 检索命中即更新，排序下沉用
  created_by, created_at,
  updated_by, updated_at    -- 编辑审计就这四根，不建历史表
)

-- digest（编译出来的块，一块一行）
veda_memory_digests (
  id, scope_type, scope_id,
  block,                    -- 'topic' | 'charter' | 'profile'
  topic,                    -- block='topic' 时用
  content TEXT,             -- 拼装好的 markdown
  source_memory_ids JSON,   -- 这次编译选中了哪些记忆
  compiled_at, dirty, truncated,
  UNIQUE(scope_type, scope_id, block, topic)
)
```

**砍掉的列，和为什么**（相对 08-07 初稿）：

- `state`（active/pending/invalidated/revoked）——没有状态机了。错了就改，不要就删
- `superseded_by` / `origin_memory_id`——取代链和晋升链被「直接编辑」替代
- `confidence`——Zep 的 fact rating（写入时 LLM 打重要性分）2026-02 被官方整体弃用，
  这条路被亲手证伪；derived 的低权重由 `kind` 本身表达，读侧按 kind 打折
- `usage_count`——排序下沉用 `last_used_at`（访问新近度）就够，修剪等真有膨胀问题再说

再加一个共享的 Milvus collection 存记忆向量，scope 相关字段做标量过滤——
和现在 `veda_summaries` 双写是同一个模式（写侧 outbox 自愈）。
**读侧 Milvus 只产候选，MySQL 是唯一真相**，见 §8。

digest 的 `dirty` 清零用带版本号的条件更新（编译期间有新写入就保持脏、下窗重编），
或者退一步靠周期性全量重编兜底——两种都行，实现时选便宜的。

## 7. 写入：新增，或者编辑旧的

工具五个：

```
memory_save(content, kind, topic?, source_ref?, expires_at?, scope?)
memory_update(id, content?, topic?, source_ref?, expires_at?)
memory_delete(id)
memory_search(query, ...)
memory_context(...)          -- 见 §8
```

规则：

- **默认写个人域**；`scope='team'` 直接写团队域，零门槛，靠署名负责（见 §13）
- **save 会把近邻带回来**：服务端为 topic 归属反正要做一次向量检索，顺手返回 top-3
  相似的旧记忆。写入方一看：该改的是旧条，就去 `update`；确实是新事实，才落新条。
  这是近重复治理的最便宜形态，也和 Claude Code 记忆的纪律同款
  （先查有没有覆盖的，有就更新，错了就删，别堆重复）
- **精确重复由 DB 唯一键挡**（`content_hash`）。mem0 的应用层 check-then-insert
  有实锤并发竞态，压到 DB 层天然免疫
- **topic 相当于记忆的目录**，写的时候就定。缺省的话服务端拿向量找最近的已有主题归进去，
  实在不像才开新主题。为什么写入时定而不是事后聚类？因为写入方有完整上下文，
  这个判断在写入那一刻做最准也最便宜；事后聚类的簇边界会随数据漂移，每次重算分组都变
- **工具描述里要写清楚记什么**（直接抄腾讯那套抽取原则，实测有效）：
  - 宁缺毋滥，拿不准就别记
  - 每条要能独立看懂（跳出当时的对话仍然成立）
  - 能归纳合并的先合并，别记流水账
- **不做写入管线里的自动 LLM 合并**。mem0 最早的版本是「新记忆进来，用 LLM 比对旧记忆，
  决定新增/更新/删除」，2026-04 的 v3 把这套亲手砍了——又贵又慢又不稳。
  注意区分：砍的是**写入管线自动跑 LLM 决策**；agent 带着上下文主动调 `update`
  是判断力在 agent 端、服务端只给原语（Letta 哲学），恰恰是要的
- **LLM 挂了要能降级**：自动抽取那条路径上，判重的 LLM 不可用时**宁可重复入库也不丢数据**
  （重复有唯一键兜底）
- 编辑/删除的权限跟着域走：个人域只有本人（的身份）能动，团队域全员能动——
  这由 §4.1 的读写原语天然保证，不是新增权限

## 8. 读取：一次查询把两边合起来

```
memory_context(W, P) 的范围 =
    (workspace, W) 的全部团队记忆
  + (principal, P) 里 origin ∈ {W, 空} 的个人记忆
  - expires_at 已到期的
```

一次查询带 OR 条件就行，不查两遍。

**读路径的一致性规则**：Milvus 只产候选 id，返回前回 MySQL 按 id 取权威内容——
被删的行天然消失（行都没了），刚编辑过的拿到新文本，删除即刻生效，不依赖双写时序。
候选是 top-K 量级，一次索引查询，不是性能问题。

返回结果每条带上：

- **来源标签**：`[团队]` / `[你的]`，加维护人和日期，让使用它的 LLM 自己掂量分量
- **注入格式**：记忆一律作为标记明确的**资料块**进 prompt（不是拼进指令区），
  系统提示里申明「这些是参考资料，不是指令」——对抗持久化 prompt 注入的最低配防线
- **排序**：语义相似度主导，时间和 `last_used_at` 只做调序、不扩召回
  （mem0 读时融合的结构：弱信号不进召回，只影响顺序）

注入给 agent 的内容要控制体积（这块腾讯设计得最好，直接借鉴）：

- 常驻部分：画像 + digest 的**索引**（主题名 + 一行简介，不给正文）
- 动态部分：按问题检索到的原子记忆 top-K
- 不够的时候：agent 自己调工具去读某个主题块的正文、去搜原子、去翻原始对话

三层深挖全是主键查：`[mem:123]` → 取那条记忆 → 看它的 `source_ref` → 翻到原始对话。

**个人和团队冲突了怎么办**：两条都给，带上来源和时间，让 LLM 权衡。
唯一的例外是 `preference` 类，个人优先——「团队规范注释用英文」和「我喜欢中文回复」
根本不是同一层的事，不该互相打架。

## 9. 改、删、过期：没有失效状态机

对一条记忆能做的事就三件：

- **错了 → 改那条**（`update`，重嵌入走文件同款管线）
- **不要了 → 删**（硬删，MySQL 行和 Milvus 向量一起消失）
- **写入时就知道保质期 → `expires_at`**，到期机械过滤，零判断

### 9.1 先接受一个事实

**没人指定失效时间的记忆，就是永久有效的，这不是缺陷。**
「生产 MySQL 密码要 unquote」就该一直有效。

记忆系统没有伸向世界的传感器，不可能自己发现某件事变了。
唯一能知道的时机是：**有新信息进来的时候**，或者**写入时就说好了保质期**。

所以对付「旧信息还占着高位」，靠的不是失效仪式，是三条：

1. **排序下沉**：检索打分算上 `last_used_at`，没人再碰的自然就沉底了
2. **带日期给出去**：让使用它的 LLM 自己对老信息打折
3. **改正要便宜**：真发现错了，谁看见谁就地改掉——这正是可编辑模型的意义

### 9.2 后台 LLM 对账：只提名，不执行

新记忆写完，异步召回相似的老记忆，让 LLM 判有没有矛盾——**发现疑似矛盾只生成一条待办**
（提给记忆的主人或团队），由人或带上下文的 agent 去改去删，LLM 自己不动手。

为什么两个域都只提名：硬删不可逆，而 LLM 的误判很具体——
「生产单节点 drain=0」和「多节点要配 drain」看着矛盾其实场景不同；
「用 MySQL」和「用 Milvus」是互补不是打架。统一提名制，机制只有一个，也最安全。

### 9.3 一个容易混的边界

**「不再被用」不是删除理由**。「生产 MySQL 密码要 unquote」一年用两次，但永远是真的。
排序下沉管「排多前」，删除管「真不真」，两条线不能串。

## 10. digest：只挑选和拼装，不做二次总结

这是本方案和所有业界实现分歧最大的地方，所以要说清楚理由。

### 10.1 为什么不让 LLM 再总结一遍

调研的各家全都在这一层让 LLM 重写（腾讯的 L2 场景块甚至鼓励「推断隐性信号」，
主动产生原文里没有的结论），而且**没有一家做引用校验**——
腾讯把记忆 id 传进了 prompt 却不强制引用，检索输出也不带 id，溯源链两头都断了。

但他们必须重写，因为他们的原子是碎片化的 fact，不重写读不通顺。
**veda 的原子记忆本身就是完整的一句话**（§7 的写入原则保证这点），
再总结一次就是复印件翻印复印件——只增加失真，不增加信息。

veda 自己也已经验证过这个结论：`GET /v1/layout` 就是「零新增 LLM 调用，纯组装既有摘要」。
digest 是同一个思路在记忆上的复刻。

### 10.2 编译流程

```
1. 标脏     记忆表任何写入/编辑/删除 → 对应 (scope, topic) 的 digest 行 dirty=1
                （和 SummarySync 的 dirty + 防抖是一个套路）
2. 后台任务 防抖 30 分钟后消费：
   a. 选材   纯 SQL：该 scope + topic 下未过期的，按 last_used_at / 时间排序取前 M 条
   b. 拼装   纯代码模板：每条渲染成 `- [mem:{id}] ({日期}) {内容原文}`
             超出 M 条就置 truncated=1，明确告诉使用者截断了
   c. 简介   唯一一次 LLM 调用（可选）：给这个块写一句话介绍。失败就不要简介，块照样能用
   d. 校验   纯代码：正文里出现的每个 [mem:id] 必须在选材集里且仍然存在，不合规的行直接剔掉
   e. 落库   单行 upsert：content + source_memory_ids + compiled_at，条件清脏（见 §6）
3. 失败     保留旧块（内容旧但可用），dirty 不清，下个窗口重试
```

选材、拼装、校验全是确定性代码，LLM 只碰一句话简介。**失真面被压缩到一行字。**

### 10.3 防膨胀

主题数要有上限。超了就强制合并或归档旧主题——这条纪律是从腾讯抄的：
它硬限 15 个场景文件，快满时强制先合并再新建，每批最多新建 1 个。
没有容量闸的话，主题会无限增殖，digest 索引本身就变成噪音。

### 10.4 一个重要提醒

腾讯有个现成的反面教材：它的抽取阶段明明产出了场景名，
但下一层完全不用、重新聚类了一遍——**写入时定的归属被白算了**。
veda 的 topic 必须真正被 digest 消费，否则就是个摆设列。

## 11. 画像：唯一需要「归纳」的地方，产物要落回原子层

「Joe 偏好最简方案」这种结论，是从十次观察归纳出来的，光靠拼装给不出来。
所以画像是唯一真正需要 LLM 归纳的环节。

关键设计：**归纳出来的结论本身写回记忆表**（`kind='derived'`），而不是只活在一段画像文本里。

```
1. 触发   某个人自上次归纳后新增的 preference/decision 类记忆 ≥20 条，或满 7 天
2. 输入   他的 preference/procedure/decision 记忆 + 现有的 derived 结论
3. 归纳   LLM 产出 0..k 条结论，每条必须列出支撑它的记忆 id；
          明确允许「没有新结论就输出空」（不硬憋）
4. 校验   纯代码：支撑 id 必须都存在，支撑数 ≥2 才收
5. 落库   写成新的 derived 记忆，source_ref = {"memory_ids": [...]}；
          和旧 derived 内容相同就跳过，明确是更新的，直接编辑旧行
```

三条护栏：

- **derived 的 origin 继承全部支撑中最严的那个**：支撑里有任何一条带 `origin=A`，
  结论就锁在 A——防止项目内的事实被归纳成「随身画像」跨项目泄露
- **读时校验支撑仍存在**：derived 进 context 前查一把支撑 id（几十条量级的 IN 查询），
  支撑被删光的跳过并标记待重推，不让查无对证的结论继续活着
- **derived 天然低权重**：由 kind 本身表达，读侧按 kind 打折，不引入 confidence 列

**为什么必须落回原子层**：腾讯的画像是一整块自由文本，单条结论没法失效，
支撑它的事实变了也无从察觉——这是个死结。写回原子层之后，
derived 结论和普通记忆享受同等待遇：能检索、能被编辑、能删、能追溯凭什么。

画像块的 digest 就是用 §10 的拼装流程，选材范围是这些 derived 记忆 + 高频偏好。

## 12. 关系怎么存

一句话判据：**会影响真假判断的关系必须存；只影响缓存重建的关系顺手存。**

| 关系 | 存在哪 | 必要性 | 用来干嘛 |
|---|---|---|---|
| 记忆 → 证据 | `source_ref` | **必须** | 追溯这条哪来的 |
| derived → 支撑记忆 | `source_ref.memory_ids` | **必须** | 支撑没了要能察觉（承重墙） |
| 记忆 → 所属主题 | `topic` | **必须** | digest 的分组键 |
| digest → 选中的记忆 | `source_memory_ids` | 顺手存 | 删除联动 + 调试 |

取代链（superseded_by）和晋升链（origin_memory_id）没了——被「直接编辑」替代，
关系矩阵比初稿少一半。

### 变动怎么传播

全是行级操作，事件驱动：

- **某条被编辑/删除** → 按 `topic` 找到 digest 标脏，下个窗口重编译；
  **删除**再查一把 `source_memory_ids`，命中当前 digest 就**跳过防抖立即重编译**——
  这样「删」才是真的闭环（检索路径靠 MySQL 复核挡住，注入路径靠立即重编译挡住，两条路同时干净）
- **某条 derived 的支撑被删光** → 读时校验跳过（§11），下次归纳窗口废弃或重推

反查用 JSON 扫描就够——derived 是画像量级，几十条，不是几百万条。真到规模了再建索引。

### 走一遍真实场景

1. 张三的 agent 记下「集成测试要加 --test-threads=1」→ mem:88，topic=testing，
   scope=team → testing 块标脏 → 30 分钟后进块
2. 两周后李四发现 SQL 测试其实要多线程——他的 agent 检索时看到 mem:88（带署名和日期），
   直接 `update` 改写内容 → 块标脏 → 下个窗口更新，署名变成李四
3. 如果有条 derived 结论引用了某条被删的记忆 → 读时跳过，下次归纳修正
4. 某条团队记忆被管理员删掉 → MySQL 行消失，检索复核天然过滤；
   `source_memory_ids` 命中 → 立即重编译，digest 里也消失

全程不用人审批，没有关系表，没有图数据库——就是几根列在后台任务里跑。

## 13. 团队治理：wiki，不是期刊

**团队域全员可写、可编辑、可删；责任靠署名和日期，不靠门槛。**

08-07 初稿设计过一套「个人写入 → pending → 人工审批 → 团队生效」的晋升流程，
**08-11 拍板砍掉**，理由：

- **审批队列没有阻塞方，必然腐烂**。code review 能运转是因为它挡着别人急需的合并；
  记忆晋升谁也不挡——提议的人自己个人域里已经有这条了，他的 agent 照常工作，
  审不审对他零影响。没人催审、管理员也没动力看一句话的琐碎事实，
  结果就是队列堆积、团队域空转
- **审批买不到它声称的东西**。调研里 GateMem 抓的越权泄露、删除不生效，
  靠的是分域和硬删解决，和审批无关。审批真正买到的只有「已审」标签的纯度——
  在公司内互信环境里，署名 + 日期 + 人人可纠错，提供的信任够用
- **wiki 的先例**：公司知识库（wiki/confluence）从来是人人可编辑、靠署名和历史追责，
  没有哪家给每次编辑加审批，也没有因此塌掉

**明确接受的代价**：没有前置闸，一条错误事实或一次 prompt 注入写进团队域，
立刻进全组 agent 的 context。兜底是四样：署名可追（`created_by`/`updated_by`）、
人人可改可删、注入时按资料块框住（§8）、admin 可清（既有 token 的管理面板）。
真出大问题再考虑加闸——**现在不预留机制**（YAGNI，无兼容包袱）。

其余几条：

- 只读的 `wk_` 映射现有语义：能搜能读，不能写
- **共享 key 的写入面要收敛**：tunnel 场景写记忆用**提问人**的身份落他的个人域
  （企微 user_id 是权威身份，§5），bot 自己的 key 不往团队域写；
  自动摄入的规则见 §15 M3
- **不做每条记忆单独授权**（腾讯有这一档，是复杂度陷阱）。两档可见性够用

## 14. 多个 workspace 怎么关联：存储层不关联，人是连接点

```
              张三 (principal P)
              个人域：随身偏好 + 各项目的私人笔记（带 origin 标记）
             ╱            │            ╲
      workspace A    workspace B    workspace C    ← 三个团队域彼此完全独立
      检索 = 团队A + P(origin ∈ {A, 空})
```

- 张三在 3 个项目 = 1 个个人域 + 3 个团队成员关系。
  他的偏好一处生效处处生效；项目笔记各归各的，不串台
- **团队之间永不互见**。A 团队的记忆对 B 团队不可见
- 两个团队都需要的事实（比如「公司 OTLP collector 地址」）往上走一级——
  `scope_type='account'` 的组织域，同一套机制第三次复用。**第一阶段不做，但模型里留好位置**
- agent 同样对待：CI 机器人、跨项目的 coding agent 也是 principal，也有自己的个人域

### 两个要标注的遗留问题

1. **同一个人从不同入口进来算两个人**：走平台网关（passport 名）和走企微（企微 userid）
   第一阶段是两条 principal 记录。公司内这两者多半同根，后面加个映射表就能合并，但要实测。
2. **个人记忆跨团队走的治理边界**：个人域跟着人跑，A 团队的管理员管不到张三的个人笔记。
   公司内部署这是合理的（那是他自己的脑子），但可以加一道闸：
   只有 preference/procedure 类允许 `origin` 为空（真正随身），
   fact 类强制带 origin——防止项目内的事实披着「个人偏好」的皮溜出项目边界。
   （画像侧的对应护栏是 §11 的 origin 继承。）

## 15. 分几步做

| 阶段 | 做什么 | 依赖 |
|---|---|---|
| **M1** | 原子记忆最小可用：两张表 + Milvus collection + MemoryService + 5 个 MCP 工具（save/update/delete/search/context）+ REST；个人/团队分域；save 返回近邻 | 无 |
| **M2** | 读侧完整：MySQL 候选复核、`memory_context` 注入模板（标签/日期/资料块框）、expires_at 过滤、last_used_at 埋点、对账提名任务 | M1 |
| **M3** | 自动摄入 + digest + 画像：第一个来源用 tunnel 的 qa_log（现成的团队对话流） | M2 |
| **M4** | console 记忆面板：浏览 / 编辑 / 删除 / 热度，挂既有 admin token | M1 |

M1 就能自己用起来：coding agent 通过 MCP 记 repo 的坑，企微场景记团队确认过的事实。

**M3 的摄入规则现在就定死**：自动抽取的记忆**一律落提问人的个人域**
（私聊更是只进本人域），团队域永远只收显式写入——人或 agent 主动调 `scope='team'`。
自动管线不直接生产「团队事实」，团队想要，由人把自己域里的好东西转写过去。

**digest 可以往后放**：mem0 根本没有这一层也活得很好。真实的触发条件是
「某个域的原子超过几百条，开场检索开始出噪音」。到那时先拿 qa_log 试编译一个主题块
验证准确率，再决定铺开。

## 16. 明确不做

| 不做的事 | 理由 |
|---|---|
| 审批流 / 状态机 | 08-11 拍板砍掉：审批队列无阻塞方必然腐烂;GateMem 抓的问题靠分域+硬删解决,与审批无关;wiki 模式先例充分（见 §13） |
| supersede 取代链 / 软删 | 「直接编辑/硬删」替代;硬删对「彻底遗忘」反而是最强保证 |
| 编辑历史表 | v0 不做;记忆是一句话量级,改坏了重写便宜;署名+日期够追责 |
| confidence 列 / 写时重要性打分 | Zep fact rating 2026-02 被官方弃用,写时 LLM 打分证伪;derived 低权重由 kind 表达 |
| key 轮换/迁移产品化 | principal 标签手工重挂即可 |
| 记忆专属的权限动作 / RBAC | principal 只做归属标识;数据面沿用 wk_/平台 authz,admin 沿用既有 token |
| 图数据库 / 实体关系抽取 | 被三方证伪：mem0 从开源版删光了全部图存储代码；腾讯用 SQLite；Zep 的检索大头本来就是语义+BM25（veda 已有），它真正的创新（时序）用几根列就能近似 |
| 写入管线自动 LLM 增删改 | mem0 原作者做过然后砍了，贵、慢、不稳（agent 主动 update 不在此列，见 §7） |
| 双时间线（事件时间 + 系统时间） | Zep 那套是为了「回答历史上任一时刻什么为真」，veda 没有这个需求 |
| 自由聚类分组 | 簇边界随数据漂移，每次重算分组都变，digest 跟着震荡，而且簇没有名字 |
| 每条记忆单独授权 | 两档可见性够用 |
| 重建一套账号权限体系 | 平台鉴权外置已经解决了 |
| 逐条写入即演化（A-MEM 那套） | 研究代码，实现有 bug，产物不持久化 |
| LLM 代理劫持接入（腾讯的做法） | 侵入性太高，veda 有 MCP 这个更干净的接入面 |
| KV-cache / 参数化记忆（MemOS） | 研究产品 |

## 17. 业界调研结论（2026-08-07 初查，2026-08-11 增补核查）

三轮 fan-out 调研含代码级核实（08-07），加二轮机制深挖与新项目扫描（08-11）。

### 各家怎么做的（08-07）

| 项目 | 关键机制 | 值得抄的 | 不能抄的 |
|---|---|---|---|
| **mem0** | 2026-04 的 v3 把写时 LLM 决策砍了，改成只追加 + hash 去重，冲突放到读时用多信号融合 + 时间推理解决；org/project/user/agent 多级 scope | 存储骨架；读时融合结构；scope 模型 | 无（最接近 veda 的形态） |
| **Letta**（原 MemGPT） | 常驻 context 的 memory block（agent 可以自己编辑）+ 外部 archival；sleep-time agent 后台巩固 | 「记忆操作全部做成工具，判断力在 agent 端，服务端只给原语」这个哲学；「没有实质更新就直接结束」的跳过路径 | 它是 agent 运行时，前提是你托管 agent——veda 不托管 |
| **腾讯 TencentDB-Agent-Memory** | 四层管线 L0→L3；LLM 自主归档，硬限 15 个场景文件 | 抽取三原则；注入预算设计；容量闸纪律；判重全链路降级不丢数据 | L2/L3 重度二次摘要且无引用校验，溯源两端都断 |
| **Zep / Graphiti** | 时序知识图谱：事实带生效/失效时间；group graph 做共享 | 时序语义（几根列近似）；context 里每条事实带日期 | Neo4j；community 聚类 |
| **Memobase** | 预定义主题槽位 + 双重尺寸闸 | 槽位约束 + 防膨胀闸 | 画像行没有引用 |
| **LangMem** | 后台记忆管理器 + 防抖执行器 | 防抖机制 | 引用无机械校验 |
| **basic-memory** | 一个主题一个 markdown 文件，写入方当场决定放哪 | 「写入时归属」的活证据 | —— |
| **A-MEM** | 论文项目，写入同步 LLM 改写邻居 | —— | 有实打实的 bug，不要参考 |

### 08-11 增补核查（机制级）

- **mem0 细节**：Memory Decay = 每条记忆存最近 20 次访问时间戳，对相关性分乘 0.3×–1.5×
  缩放，只调序不扩召回——「检索即反馈」零成本，`last_used_at` 的用法照此。
  教训：MD5 精确 hash + 应用层 check-then-insert 有实锤并发竞态（→ veda 压 DB 唯一键）
- **Zep**：fact rating（写时 LLM 打 0-1 分）**2026-02 被官方整体弃用**——写时打分证伪
  （→ veda 不设 confidence 列）。context 行格式「事实 (from - to/present)」值得抄。
  Graphiti 的 `remove_episode` 是业界唯一生产级删除传播（计数式），但它没有 digest 层
- **Letta**：共享 block 并发语义 = append 安全 / replace 乐观校验 / 整块重写 last-write-wins，
  官方建议「单 owner 做重编辑」——veda 的 digest 单后台任务天然符合
- **腾讯 v2.0**（2026-08-03 开源）：团队记忆枢纽形态，四类资产 + 四档可见性 ACL + 版本，
  但无仲裁无治理闭环——媒体评语「stores, doesn't adjudicate」
- **OpenViking**（字节，2026-01 开源，28k star）：`viking://` 文件系统心智 +
  写入时 L0/L1/L2 分层摘要，与 veda 文档三层最接近的活项目，**持续对标对象**；摘要无校验
- **cognee**（29.9k star）：content-hash 去重、dataset 级 ACL 业界最完整；图管线定位，不动摇不做图的结论
- **ReMe**（MemoryScope 已改名重定向）：Markdown 文件即记忆，「Memory as File」阵营
- **文件阵营先例**（支撑 08-11「可编辑」拍板）：Claude Code 自身记忆（一条一文件，
  错了改、过时删，零状态机）、basic-memory、ReMe——可编辑模型有一整个活得很好的阵营
- **GateMem**（arXiv 2606.18829，2026-06）：多主体共享记忆 benchmark。
  现有系统越权泄露率 8.9%–33.9%、删除后仍答出率 2.3%–37.2%，原文结论
  「no method simultaneously achieves strong utility, robust access control, and reliable
  active forgetting」。veda 的分域 + 硬删 + MySQL 复核目标是这两项**确定性 = 0**，
  直接做成集成测试断言（框架 MIT，探针可复用）
- **MINJA**（NeurIPS 2025）：纯对话诱导 agent 自己写入恶意记忆，98.2% 注入成功率；
  OWASP 已把 memory poisoning 列为 Agentic Top 10 的 ASI06。业界推荐防线 =
  写边界 + 来源标签 + 隔离。veda 取来源标签、资料块注入、分域、人人可删四样；
  **写边界（审批）明确不取**，是 §13 写明的赌注

### 跨项目的共同结论

1. **写路径在退火不在加码**——mem0 亲手砍掉自己发明的复杂写路径，腾讯只检测冲突不自动合并
2. **图数据库在退场**——mem0 从开源版删光，腾讯用 SQLite，Zep 的核心创新可以用列近似
3. **分层检索是共识**——高层铺底、按需下钻，和 veda 的文档三层同构
4. **写入时归属是主流**——MIRIX/memU/OpenViking/ReMe/basic-memory 全是写入时定归属，事后聚类是少数派
5. **巩固都是后台低频任务**——形态就是 veda 的 outbox worker + 防抖
6. **共享域的可见性控制已有多家在做**（腾讯 v2.0 四档 ACL、cognee dataset ACL、MemOS cube
   读写列表），但**治理闭环——删除全链路传播、可测的遗忘、矛盾有人管——没有任何一家做完整**
7. **拼装式 digest + 引用机械校验没有任何一家做**（11 家复核，0 家）——veda 真正的差异化

### 选型总结

**没有一家能整体照搬。** 最终配方：**mem0 v3 的存储骨架和读时融合 + 文件阵营的可编辑模型 +
Letta 的接口哲学 + 腾讯的产品形态和注入预算 + Zep 的时序零件，轻治理自研。**

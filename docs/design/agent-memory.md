# Agent / 团队记忆（设计提案）

> **状态：提案，未排期，一行代码没写。** 本文记录 2026-08-07 的业界调研结论和多轮讨论后的方案定稿，
> 供拍板用。拍板后再决定是进 `docs/plans/` 开正式计划，还是继续留在方向池。
> 文中所有能力都是「打算做」，不是「已经有」。

---

## 1. 一句话说清楚这是什么

veda 现在存的是**文档**：你传一个文件进来，它切块、做摘要、能搜、能问答。

这个提案是让 veda 再存一类东西：**记忆**——一句话一条的事实，比如

- 「集成测试必须加 `--test-threads=1`」
- 「生产节点 .85 上没有 mysql 客户端，操作要从 Mac 走 SSH 隧道」
- 「Joe 偏好最简方案，复杂优化要有证据才上」

这些东西不适合当文件传（太碎、随时变、经常是某个人某次踩坑得来的），但恰恰是 agent 每次开工最需要先知道的。

同时要分清两种记忆：**个人的**（我自己的笔记和偏好）和**团队的**（全队认可的事实）。
两者要能并存，互不污染，个人的东西能「提交」成团队的。

---

## 2. 为什么值得做

三条理由：

1. **现有底座基本够用**。要用的东西 veda 都有了：多租户、混合检索、embedding/LLM 管线、
   后台任务（outbox）、MCP 接入面、管理后台。新写的代码主要是两张表、一个 service、
   几个工具、一条后台任务。
2. **记忆和证据在同一个库里**——这是别人给不了的。团队记忆可以直接指向同 workspace 的文档、
   qa_log 记录；`/v1/answer` 回答问题时可以同时用「文档说了什么」和「团队记过什么」，
   两边互相印证。mem0、Letta、Zep 都是纯记忆系统，证据在别的地方。
3. **团队记忆的治理是行业空白**（详见 §11 调研）。谁都做了「个人记忆」，
   但「一条记忆怎么才算被团队认可、谁批的、哪来的、撤销后能不能彻底消失」没人做好。
   veda 的 Account→Workspace 加外部鉴权，正好是别人缺的骨架。

---

## 3. 三层结构，和文档那套不是一回事

记忆分三层。**注意不要用 L0/L1/L2 命名**——文档那套是「摘要在上、原文在下」，
记忆这边正好反过来（原始对话在下、摘要在上），同名反向会把人搞晕。就叫这三个名字：

| 层 | 是什么 | 例子 | 特点 |
|---|---|---|---|
| `episodes` | 原始对话/会话记录 | 企微群里的一次问答、一段 coding 会话 | 只追加不改，不进日常检索，只用来溯源 |
| `memories` | **原子记忆**（一条一个事实） | 「集成测试要加 --test-threads=1」 | 检索主力，本方案的核心 |
| `digest` | 编译出来的视图 | 「testing 主题块」「张三的偏好画像」 | 派生产物，丢了能从原子层重建 |

原子记忆有两个来源：

- **agent 主动写**（第一阶段只做这个）：agent 觉得某件事值得记，直接调工具存一条
- **从对话里自动抽**（第三阶段）：后台任务读 episodes，用 LLM 抽出原子事实

## 4. 个人和团队怎么分

### 4.1 分在存储位置上，不是分在一个标记位上

早期想法是一张表加一个 `visibility` 列（private/team），靠查询条件过滤。**这个方案被否了。**

原因很实际：那意味着同事的私密笔记和团队记忆躺在同一个查询范围里，
不泄露全靠「每一条 SQL 的 WHERE 都写对」。学术界的 GateMem 测试专门测过这个，
现有记忆系统在多人共享场景下普遍会把越权内容和已删内容检出来。

改成**位置分离**：

```
每条记忆有一个归属 = (scope_type, scope_id)

团队记忆 → (workspace, W)     存在团队域里
个人记忆 → (principal, P)     存在个人域里，压根不在 W 的范围内
```

这样隔离强度就等于 veda 现有的 workspace 隔离——同一根过滤列，同一套机制，
一条 WHERE 写错也漏不出去。

工程上不会爆炸：记忆用**一个共享的 Milvus collection + scope 列过滤**
（学 fs workspace 的做法，不是 db workspace 那种一个 workspace 一个 collection）。
几千个员工就是几千个 scope 值，不是几千个 collection。

### 4.2 个人记忆还要再切一刀

「个人记忆」其实是两种东西，混在一起会串味：

- **随身偏好**：「Joe 喜欢中文回复」「偏好最简方案」——跟着人走，在哪个项目都该生效
- **项目内私人笔记**：「这个 repo 测试要单线程」「.85 的 MySQL 走隧道」——只在那个项目有意义，
  带到别的项目是噪音，甚至是信息泄露

实现只需要一根列：个人域的记忆带 `origin_workspace_id`。
项目笔记带上它，随身偏好留空。

这和 Claude Code 的 `~/.claude`（全局）+ 项目内记忆是同一个结构，
ChatGPT 的 user memory × project 也是这么切的——行业在这一刀上完全一致。

## 5. 「人」这个概念要新建，但成员管理不要重建

veda 现在有租户（Account→Workspace），但没有「人」。要加一张最小的表：

```sql
veda_principals (
  id, kind ('human' | 'agent'),
  source ('gateway' | 'wecom' | 'key'),
  external_id, display_name
)
```

第一次见到就自动建一条（和现在 `ensure_account` 自动开户一个套路）。

身份从哪来——三个现成的来源，都已经在跑：

| 接入面 | 身份来源 | 可靠程度 |
|---|---|---|
| 平台网关面 | `GatewayUser`（平台鉴权背书） | 权威 |
| tunnel（企微） | 提问人 user_id（企微背书） | 权威 |
| 原生 `wk_` / MCP | **key 就是身份**（一人一把 key，或一个 agent 一把） | 够用 |

第三行要说明白：原生面没有登录态，所以「一把 key = 一个身份」，
**共享 key 就等于共享记忆**。这个边界诚实、说得清，而且零新机制——
tunnel 已经在这么干了（一个 bot 一把 key）。想让 MCP 下的每个人有自己的私密记忆？
给每人发一把 `wk_` 就行，key 的增删改查是现成的。

**成员管理（谁能进哪个 workspace）不做**。平台鉴权已经外置了，平台就是成员系统；
原生面 key 表挂个 principal 标签就是轻量成员表。veda 自己再建一套账号权限体系是最大的过度设计。

## 6. 数据模型

两张新表。所有关系都做成**行上的列**，不建关系表、不建边表——关系表是通往图数据库的第一步，veda 不迈。

```sql
-- 原子记忆
veda_memories (
  id,
  scope_type,               -- 'workspace' | 'principal'
  scope_id,
  origin_workspace_id,      -- 个人域用：项目笔记带上，随身偏好留空
  topic,                    -- 主题，相当于记忆的「目录」，见 §7
  kind,                     -- 'fact'|'preference'|'decision'|'procedure'|'derived'
  content,
  content_hash,             -- 去重用
  confidence,
  source_ref JSON,          -- 证据来源：普通记忆指向 episode / qa_log / 文件路径；
                            -- derived 记忆指向支撑它的那批记忆 id
  origin_memory_id,         -- 晋升来源：团队那条指回个人原件
  superseded_by,            -- 被哪条取代
  state,                    -- 'active'|'pending'|'invalidated'|'revoked'
  expires_at,               -- 可空，写入时就知道保质期的才填
  invalidated_at,
  usage_count, last_used_at,
  created_by, approved_by, created_at, updated_at
)

-- digest（编译出来的块，一块一行）
veda_memory_digests (
  id, scope_type, scope_id,
  block,                    -- 'topic' | 'charter' | 'profile'
  topic,                    -- block='topic' 时用
  content TEXT,             -- 拼装好的 markdown
  source_memory_ids JSON,   -- 这次编译选中了哪些记忆
  compiled_at, dirty, truncated,
  UNIQUE(scope_type, scope_id, block, topic)
)
```

再加一个共享的 Milvus collection 存记忆向量，scope 相关字段做标量过滤——
和现在 `veda_summaries` 双写是同一个模式。

## 7. 写入：尽量简单

工具长这样：

```
memory_save(content, kind, topic?, supersedes?, expires_at?)
```

规则：

- **只追加，不做智能合并**。写进去就是新的一条，重复靠内容 hash 挡掉。
  为什么不做合并？因为 mem0 做过——他们最早的版本是「新记忆进来，
  用 LLM 比对旧记忆，决定新增/更新/删除」，2026 年 4 月的新版本**把这套亲手砍了**，
  理由是又贵又慢又不稳。冲突留到读的时候处理。
- **topic 相当于记忆的目录**，写的时候就定。缺省的话服务端拿向量找最近的已有主题归进去，
  实在不像才开新主题。为什么写入时定而不是事后聚类？因为写入方有完整上下文，
  这个判断在写入那一刻做最准也最便宜；事后聚类的簇边界会随数据漂移，每次重算分组都变。
- **工具描述里要写清楚记什么**（直接抄腾讯那套抽取原则，实测有效）：
  - 宁缺毋滥，拿不准就别记
  - 每条要能独立看懂（跳出当时的对话仍然成立）
  - 能归纳合并的先合并，别记流水账
- **LLM 挂了要能降级**：自动抽取那条路径上，判重的 LLM 不可用时**宁可重复入库也不丢数据**
  （重复有 hash 兜底）。
- **默认写进个人域**（`origin` = 当前 workspace）。要写团队域的，先落 `pending` 等审。

## 8. 读取：一次查询把两边合起来

```
memory_context(W, P) 的范围 =
    (workspace, W) 里 state=approved 的团队记忆
  + (principal, P) 里 origin ∈ {W, 空} 的个人记忆
```

一次查询带 OR 条件就行，不查两遍。返回结果每条带上来源标签（`[团队·已审]` / `[你的]`）
和日期，让使用它的 LLM 自己掂量分量。

注入给 agent 的内容要控制体积（这块腾讯设计得最好，直接借鉴）：

- 常驻部分：画像 + digest 的**索引**（主题名 + 一行简介，不给正文）
- 动态部分：按问题检索到的原子记忆 top-K
- 不够的时候：agent 自己调工具去读某个主题块的正文、去搜原子、去翻原始对话

三层深挖全是主键查：`[mem:123]` → 取那条记忆 → 看它的 `source_ref` → 翻到原始对话。

**个人和团队冲突了怎么办**：两条都给，带上来源和时间，让 LLM 权衡。
唯一的例外是 `preference` 类，个人优先——「团队规范注释用英文」和「我喜欢中文回复」
根本不是同一层的事，不该互相打架。

## 9. 什么时候失效，谁说了算

### 9.1 先接受一个事实

**没人指定失效时间的记忆，就是永久有效的，这不是缺陷。**
「生产 MySQL 密码要 unquote」就该一直有效。

记忆系统没有伸向世界的传感器，不可能自己发现某件事变了。
唯一能知道的时机是：**有新信息进来的时候**，或者**写入时就说好了保质期**。

所以对付「旧信息还占着高位」，靠的不是失效仪式，是三条：

1. **排序下沉**：检索打分算上最近使用/使用次数，没人再碰的自然就沉底了
2. **带日期给出去**：让使用它的 LLM 自己对老信息打折
3. **改正要便宜**：真发现错了，一条 `supersedes` 就地解决

### 9.2 谁有权判失效

从最可靠到最不可靠：

| 顺序 | 谁 | 依据 |
|---|---|---|
| 1 | **写入方声明**（首选） | `memory_save(..., supersedes: 88)`——它刚部署完 / 刚被人纠正，只有它有上下文 |
| 2 | 机械规则 | 内容 hash 重复、`expires_at` 到期。零判断，不会错 |
| 3 | 后台 LLM 对账（兜底） | 新记忆写完，异步召回相似的老记忆，让 LLM 判有没有矛盾 |
| 4 | 人 | 团队记忆的终审 |

**执行权按域分开**：

- **个人域**：1、2、3 都能直接生效。错杀成本低——`invalidated` 不等于删除，
  行还在，只是不出现在检索里，发现错了翻回来即可
- **团队域**：只有 1 和 2 能直接生效，**LLM 只有提名权没有执行权**——
  发现矛盾只生成一条待审冲突，人来裁。团队记忆的价值是「敢信」，
  一旦误杀，信任塌得比丢记忆还快

第 3 条为什么只当兜底：误判很具体——「生产单节点 drain=0」和「多节点要配 drain」
看着矛盾其实场景不同；「用 MySQL」和「用 Milvus」是互补不是打架。

### 9.3 一个容易混的边界

**「不再被用」不是失效理由**。使用次数驱动的是**修剪**（个人域配额、归档），
不是**真假**——「生产 MySQL 密码要 unquote」一年用两次，但永远是真的。
失效管「真不真」，修剪管「留不留」，两条线不能串。

## 10. digest：只挑选和拼装，不做二次总结

这是本方案和所有业界实现分歧最大的地方，所以要说清楚理由。

### 10.1 为什么不让 LLM 再总结一遍

调研的五家全都在这一层让 LLM 重写（腾讯的 L2 场景块甚至鼓励「推断隐性信号」，
主动产生原文里没有的结论），而且**没有一家做引用校验**——
腾讯把记忆 id 传进了 prompt 却不强制引用，检索输出也不带 id，溯源链两头都断了。

但他们必须重写，因为他们的原子是碎片化的 fact，不重写读不通顺。
**veda 的原子记忆本身就是完整的一句话**（§7 的写入原则保证这点），
再总结一次就是复印件翻印复印件——只增加失真，不增加信息。

veda 自己也已经验证过这个结论：`GET /v1/layout` 就是「零新增 LLM 调用，纯组装既有摘要」。
digest 是同一个思路在记忆上的复刻。

### 10.2 编译流程

```
1. 标脏     记忆表任何写入/状态变化 → 对应 (scope, topic) 的 digest 行 dirty=1
                （和 SummarySync 的 dirty + 防抖是一个套路）
2. 后台任务 防抖 30 分钟后消费：
   a. 选材   纯 SQL：该 scope + topic 下 state=active 的，
             按 confidence / 使用次数 / 时间排序取前 M 条
   b. 拼装   纯代码模板：每条渲染成 `- [mem:{id}] ({日期}) {内容原文}`
             超出 M 条就置 truncated=1，明确告诉使用者截断了
   c. 简介   唯一一次 LLM 调用（可选）：给这个块写一句话介绍。失败就不要简介，块照样能用
   d. 校验   纯代码：正文里出现的每个 [mem:id] 必须在选材集里且是 active，不合规的行直接剔掉
   e. 落库   单行 upsert：content + source_memory_ids + compiled_at，dirty 清零
3. 失败     保留旧块（内容旧但可用），dirty 不清，下个窗口重试
```

选材、拼装、校验全是确定性代码，LLM 只碰一句话简介。**失真面被压缩到一行字。**

### 10.3 防膨胀

主题数要有上限。超了就强制合并或归档旧主题——这条纪律是从腾讯抄的：
它硬限 15 个场景文件，快满时强制先合并再新建，每批最多新建 1 个。
没有容量闸的话，主题会无限增殖，digest 索引本身就变成噪音。

### 10.4 一个重要提醒

腾讯有个现成的反面教材：它的抽取阶段明明产出了场景名，
但下一层完全不用、重新聚类了一遍——**写入时定的归属被白算了**。
veda 的 topic 必须真正被 digest 消费，否则就是个摆设列。

## 11. 画像：唯一需要「归纳」的地方，产物要落回原子层

「Joe 偏好最简方案」这种结论，是从十次观察归纳出来的，光靠拼装给不出来。
所以画像是唯一真正需要 LLM 归纳的环节。

关键设计：**归纳出来的结论本身写回记忆表**（`kind='derived'`），而不是只活在一段画像文本里。

```
1. 触发   某个人自上次归纳后新增的 preference/decision 类记忆 ≥20 条，或满 7 天
2. 输入   他的 active 记忆（preference/procedure/decision）+ 现有的 derived 结论
3. 归纳   LLM 产出 0..k 条结论，每条必须列出支撑它的记忆 id；
          明确允许「没有新结论就输出空」（不硬憋）
4. 校验   纯代码：支撑 id 必须都存在且 active，支撑数 ≥2 才收
5. 落库   写成新的 derived 记忆，source_ref = {"memory_ids": [...]}，confidence 低一档
6. 对齐   和旧 derived 内容相同就跳过；明确是更新的，新行 supersedes 旧行
```

**为什么必须落回原子层**：腾讯的画像是一整块自由文本，单条结论没法失效，
支撑它的事实变了也无从察觉——这是个死结。写回原子层之后，
derived 结论和普通记忆享受同等待遇：能检索、能被取代、能撤销、能追溯凭什么。

画像块的 digest 就是用 §10 的拼装流程，选材范围是这些 derived 记忆 + 高频偏好。

## 12. 关系怎么存

一句话判据：**会影响真假判断的关系必须存；只影响缓存重建的关系顺手存。**

| 关系 | 存在哪 | 必要性 | 用来干嘛 |
|---|---|---|---|
| 记忆 → 证据 | `source_ref` | **必须** | 追溯这条哪来的 |
| derived → 支撑记忆 | `source_ref.memory_ids` | **必须** | 支撑变了要能反查到它（承重墙，见下） |
| 团队记忆 → 个人原件 | `origin_memory_id` | **必须** | 谁提的、原话是什么 |
| 新记忆 → 被取代的 | `superseded_by` | **必须** | 失效链 |
| 记忆 → 所属主题 | `topic` | **必须** | digest 的分组键 |
| digest → 选中的记忆 | `source_memory_ids` | 顺手存 | 撤销联动 + 调试 |

**derived 那条为什么是承重墙**：不存的话具体死法是——
支撑它的事实后来被取代了（Joe 改口了），归纳出来的结论查无对证却继续活着，
还以高置信度进 context，没人能回答「这条凭什么、还成不成立」。

**digest 那条为什么顺手存**：digest 本来就能从原子层整体重建（和 `veda_file_extracts` 一个定位），
不存也能靠周期重编译兜底。但存了能做一件事：团队记忆被撤销时，
一条 `JSON_CONTAINS` 就知道它在不在当前 digest 里，在就**跳过防抖立即重编译**——
这样「撤销」才是真的闭环（检索路径被过滤挡住，注入路径被立即重编译挡住，两条路同时干净）。

### 变动怎么传播

全是行级操作，事件驱动：

- **某条被取代/失效** → 按 `topic` 找到 digest 标脏，下个窗口重编译，旧条自然消失；
  按 `source_ref` 反查引用了它的 derived，降一档置信度、标记待重推
- **团队记忆被撤销** → 状态置 revoked，检索过滤层**硬排除**（不是靠排序软忽略）；
  查 `source_memory_ids` 命中就立即重编译
- **某条 derived 的支撑全没了** → 下次归纳窗口按规则直接作废，不用劳烦 LLM

反查用 JSON 扫描就够——derived 是画像量级，几十条，不是几百万条。真到规模了再建索引。

### 走一遍真实场景

1. 张三的 agent 记下「集成测试要加 --test-threads=1」→ mem:88，topic=testing
   → testing 块标脏 → 30 分钟后进块
2. 两周后发现 SQL 测试其实要多线程，agent 写新条并声明 `supersedes: 88`
   → 88 失效、块标脏 → 下个窗口 88 消失，新条带新日期在列
3. 如果有条 derived 结论「张三的测试都用单线程」引用了 88
   → 自动降档待重推，下次归纳时修正或废弃
4. 如果 88 曾经晋升进团队域，后来被管理员撤销
   → 检索立刻查不到，团队块立刻重编译

全程不用人干预，没有关系表，没有图数据库——就是几根列在后台任务里跑。

## 13. 团队治理：从个人到团队要过一道闸

```
写入 ──▶ 个人域，立即生效（零门槛，写错只污染自己）
            │ 提议晋升（人或 agent 主动）
            ▼
        pending ──审核（可改写措辞、可标记取代旧的团队记忆）──▶ 团队域，approved
            └─ 驳回 ──▶ 留在个人域
```

几个要点：

- **个人域零审批是关键**。agent 会高频写，门槛设在这里就没人用了
- **晋升是新建一行不是改旧行**，团队那条用 `origin_memory_id` 指回个人原件。
  因为审核时经常要把「我发现 .85 的 MySQL 要走隧道」改写成更通用的表述，
  而「这条团队事实源自谁的哪次观察」本身就是要留的证据
- **审核点就是人工仲裁点**：批准时可以标「本条取代团队记忆 #123」，
  团队记忆之间的矛盾在这里解决，不搞自动仲裁
- **谁能批**：workspace 管理员（平台鉴权的角色），审核队列放在 console / admin 后台——骨架现成
- **不做每条记忆单独授权**（腾讯有这一档，是复杂度陷阱）。两档可见性够用
- 只读的 `wk_` 映射现有语义：能搜能读，不能写

## 14. 多个 workspace 怎么关联：存储层不关联，人是连接点

```
              张三 (principal P)
              个人域：随身偏好 + 各项目的私人笔记（带 origin 标记）
             ╱            │            ╲
      workspace A    workspace B    workspace C    ← 三个团队域彼此完全独立
      检索 = 团队A + P(origin ∈ {A, 空})
```

- 张三在 3 个项目 = 1 个个人域 + 3 个团队成员关系。
  他的偏好一处生效处处生效；项目笔记各归各的，不串台
- **团队之间永不互见**。A 团队的记忆对 B 团队不可见
- 两个团队都需要的事实（比如「公司 OTLP collector 地址」）往上走一级——
  `scope_type='account'` 的组织域，同一套机制第三次复用。
  晋升阶梯变成 个人 → 团队 → 组织，每跳都过审。**第一阶段不做，但模型里留好位置**
- agent 同样对待：CI 机器人、跨项目的 coding agent 也是 principal，也有自己的个人域

### 两个要标注的遗留问题

1. **同一个人从不同入口进来算两个人**：走平台网关（passport 名）和走企微（企微 userid）
   第一阶段是两条 principal 记录。公司内这两者多半同根，后面加个映射表就能合并，但要实测。
2. **个人记忆跨团队走的治理边界**：个人域跟着人跑，A 团队的管理员管不到张三的个人笔记。
   公司内部署这是合理的（那是他自己的脑子），但可以加一道闸：
   只有 preference/procedure 类允许 `origin` 为空（真正随身），
   fact 类强制带 origin——防止项目内的事实披着「个人偏好」的皮溜出项目边界。

## 15. 分几步做

| 阶段 | 做什么 | 依赖 |
|---|---|---|
| **M1** | 原子记忆最小可用：两张表 + Milvus collection + MemoryService + 3 个 MCP 工具 + REST；个人/团队域分离；晋升先落 pending | 无 |
| **M2** | 生命周期 + 上下文：supersedes / 保质期 / 使用次数埋点 / 合并检索 + `memory_context` 模板 | M1 |
| **M3** | 自动摄入 + digest + 画像：第一个来源用 tunnel 的 qa_log（现成的团队对话流） | M2 |
| **M4** | 治理面完整：console 审核队列、来源展示、组织域评估 | M1（审核 UI 部分） |

M1 就能自己用起来：coding agent 通过 MCP 记 repo 的坑，企微 bot 记团队确认过的事实。

**digest 可以往后放**：mem0 根本没有这一层也活得很好。真实的触发条件是
「某个域的原子超过几百条，开场检索开始出噪音」。到那时先拿 qa_log 试编译一个主题块
验证准确率，再决定铺开。

## 16. 明确不做

| 不做的事 | 理由 |
|---|---|
| 图数据库 / 实体关系抽取 | 被三方证伪：mem0 从开源版删光了全部图存储代码；腾讯 16.7k star 的项目只用 SQLite；Zep 虽然用图，但它的检索大头本来就是语义+BM25（veda 已有），它真正的创新（时序）用几根列就能近似 |
| 写入时用 LLM 决定增删改 | mem0 原作者做过然后砍了，贵、慢、不稳 |
| 双时间线（事件时间 + 系统时间） | Zep 那套是为了「回答历史上任一时刻什么为真」，veda 没有这个需求。用单时间线：`invalidated_at` 就是「取代动作发生的时刻」，不是猜出来的世界时间 |
| 自由聚类分组 | 簇边界随数据漂移，每次重算分组都变，digest 跟着震荡，而且簇没有名字 |
| 每条记忆单独授权 | 两档可见性够用 |
| 重建一套账号权限体系 | 平台鉴权外置已经解决了 |
| 逐条写入即演化（A-MEM 那套） | 研究代码，每次写入都同步跑 LLM 改写邻居，而且实现有 bug（改的不是邻居而是最早的 k 条），产物还不持久化 |
| LLM 代理劫持接入（腾讯的做法） | 侵入性太高，veda 有 MCP 这个更干净的接入面 |
| KV-cache / 参数化记忆（MemOS） | 研究产品 |

## 17. 业界调研结论（2026-08-07，附出处）

三轮 fan-out 调研，含代码级核实。

### 各家怎么做的

| 项目 | 关键机制 | 值得抄的 | 不能抄的 |
|---|---|---|---|
| **mem0** | 2026-04 的 v3 把写时 LLM 决策砍了，改成只追加 + hash 去重，冲突放到读时用多信号融合 + 时间推理解决；org/project/user/agent 多级 scope | 整个存储和写入骨架；scope 模型和 veda 的 Account/Workspace 几乎 1:1 | 无（最接近 veda 的形态） |
| **Letta**（原 MemGPT） | 常驻 context 的 memory block（agent 可以自己编辑）+ 外部 archival；sleep-time agent 后台巩固；多 agent 挂同一个 block 就是共享记忆 | 「记忆操作全部做成工具，判断力在 agent 端，服务端只给原语」这个哲学；触发节奏（消息数水位）；「没有实质更新就直接结束」的跳过路径 | 它是 agent 运行时，前提是你托管 agent——veda 不托管。仓库已标 legacy |
| **腾讯 TencentDB-Agent-Memory** | 16.7k star，默认分支就是团队记忆中枢形态；四层管线 L0→L3；分组靠「LLM 自主归档」（带文件读写工具自己决定更新/合并/新建，硬限 15 个场景文件） | 抽取三原则（宁缺毋滥/独立完整/归纳合并）；注入预算设计（画像给全文、场景块只给索引、工具回落限 3 次）；容量闸纪律；判重全链路降级不丢数据 | 引擎最弱的部分：L2/L3 是重度二次摘要，鼓励推断出原文没有的结论；id 传进 prompt 但不强制引用、检索输出不带 id，**溯源两端都断**；没有任何机械校验；旧记忆合并后已生成的摘要不失效 |
| **Zep / Graphiti** | 时序知识图谱：事实带生效/失效时间，矛盾时让旧事实失效而不是删除；group graph 做共享 | 时序语义（用几根列近似）；给 agent 的上下文里每条事实带日期区间 | Neo4j；community 聚类；它的增量更新是原地覆盖无 diff 无引用，是画像漂移的标准反例 |
| **Memobase** | 预定义主题槽位 + 攒批 flush + 每条事实判 更新/追加/拒收；双重尺寸闸（槽超限压缩、子主题超限重组） | 槽位约束 + 出格丢弃（对应 veda 的 topic 归属）；两道防膨胀闸 | 画像行本身没有引用 |
| **LangMem** | 后台记忆管理器增量更新；防抖执行器（同一会话重复提交就取消旧任务重新计时） | 防抖机制直接可抄 | 引用只在 prompt 里要求，没有机械校验 |
| **basic-memory** | 3.6k star 活跃项目，一个主题一个 markdown 文件，写入方当场决定放哪，没有后台巩固管线 | 「写入时归属」的活证据 | —— |
| **A-MEM** | 论文项目，每次写入同步跑 LLM 改写邻居记忆 | —— | 有实打实的下标 bug，产物不持久化，不要参考 |

### 跨项目的共同结论

1. **写路径在退火不在加码**——mem0 亲手砍掉自己发明的复杂写路径，腾讯只检测冲突不自动合并
2. **图数据库在退场**——mem0 从开源版删光，腾讯用 SQLite，Zep 的核心创新可以用列近似
3. **分层检索是共识**——高层铺底、按需下钻，和 veda 的文档三层同构
4. **生命周期就是几个列**——腾讯用 confidence/expires_at/last_used_at/usage_count 撑起全部管理
5. **巩固都是后台低频任务**——形态就是 veda 的 outbox worker + 防抖
6. **团队治理是空白**——scope 分层有共识，但权限、晋升审核、成员间矛盾仲裁没人做好。
   Zep 的 group graph 没有权限模型，ChatGPT 的项目共享记忆是黑盒，mem0 有 scope 无审批。
   学术界的 GateMem 测试实测：现有系统在多主体共享下普遍泄露越权和已删信息
7. **拼装式 digest + 引用机械校验没有任何一家做**——这是 veda 可以真正差异化的地方

### 选型总结

**没有一家能整体照搬。** 如果必须选一个当底座，选 mem0 v3——只有它和 veda 是同一种东西
（服务端 + 可插拔向量库 + 多租户）。其余三家当底座都要 veda 扭曲自己：
Letta 是 agent 运行时，腾讯是单机一体箱，Zep 押注图谱。

最终配方：**mem0 v3 的存储和写入骨架 + Letta 的接口哲学 + 腾讯的产品形态和注入预算 +
Zep 的时序零件，治理层自研。**

# veda-tunnel 方向调研（2026-07-13）

> 输入：企微 aibot 长连接协议能力面实证（官方文档 101463/100719/101027/101031/101032/101138/91770 + 官方 SDK 交叉验证，逐项标注证实等级）+ 已承诺分期（answer plan §12：P1 流式/L1，P2 多轮/db kind）+ 生产现状（.95 单实例，DAL 知识库真实服务中）。

## 协议能力速查（本次实证的增量认知）

**可用而未用**：
- `aibot_send_msg` 主动推送（用户发过一次消息即永久解锁该会话，无 48h 过期条款；30 条/min、1000 条/h，与回复合并计费）
- `response_url`（每条消息/卡片点击自带，1 小时有效、一次性）——异步补发通道
- 模板卡片 ×5（文本通知/图文/按钮/投票/多选）+ `template_card_event` 点击回调（5s 内可原地更新卡片）
- **`feedback_event` 点赞点踩**（stream 首帧设 `feedback.id` 即激活；踩带不准确原因枚举 1-4）
- 单聊收 image/file（payload 自带 url+aeskey，AES-256-CBC 解密，≤100M，url 5 分钟有效）；**voice 直接给官方转写文本**
- `quote` 引用提问：用户引用任意消息追问时，**被引消息全文随回调下发**（六种类型完整结构）
- `enter_chat` 欢迎语事件（当天首次进单聊）
- finish 帧可带 base64 图片混排（≤10 张×10M）；`<think>` 标签展示思考过程
- markdown-v2 子集：标题/表格/代码块/链接/图片/嵌套列表

**做不了（证伪，别再想）**：消息撤回；群生命周期事件（进群/被拉群）；用户名字/群名（只有 userid/chatid）；群聊收图片文件（仅单聊）；被动回复发文件（仅主动推送可以）。

## 候选方向

### T1 质量遥测闭环：问答日志 + 点赞点踩 ★ 最优先

**做什么**：① tunnel 落一张 `veda_tunnel_qa_log`（ts / bot / chattype / userid / query / outcome=answered|no_context|error / hit_count / citation 数 / latency_ms / feedback）；② 每条 stream 回复设 `feedback.id`，`feedback_event` 回来更新该行（type + 不准确原因）；③ console/tunnel 页加统计视图：日答题量、no_context 率、踩率、bad case 列表（点踩 + no_context 的 query 清单）。

**为什么最优先**：DAL 真题评审（answer DoD-4）现在靠人肉收集——这个表就是自动收集器；`no_context` 的 query 列表 = **知识库内容缺口清单**（运营者最想要的东西）；踩 + 原因枚举 = 免费标注流，直接驱动 P1 组装参数调优。质量飞轮的地基，其他一切优化都需要它来度量。

**成本**：中低。tunnel 建表+埋点（handler 已有 answer ok/error 日志点位）、feedback 事件分支、console 一个只读视图。隐私注意：query 原文落库要在文档里明示（内部知识库场景可接受；userid 可选脱敏）。

### T2 SSE 流式回答（P1 已承诺）

**做什么**：answer plan §12 的既定设计——`LlmProvider.chat_stream()`（OpenAI 兼容 SSE）→ `/v1/answer` 流式变体 → tunnel 逐帧刷新（协议：同 `stream.id` 全量替换、单帧 ≤20480 字节、10min 窗口，均已证实）。终帧 citations 权威。可选 `<think>` 展示。

**为什么**：现在用户等 7-9 秒白屏（占位帧只是不超时）。首 token 即出是体感差距最大的单项改进。

**成本**：中。设计已在 plan，无未知数。

### T3 tunnel 运维底座：OTLP 指标 + down 告警

**做什么**：tunnel 接公司 OTLP（server 有完整先例可抄）：答题量/延迟分位/错误率/conn_state。重点是 **bot down 告警**——现在 conn_state 只是心跳列，掉线没人知道，直到用户抱怨。

**为什么**：生产服务零监控是真实缺口；成本低（抄 server 的 obs 模块）。

**成本**：低中。

### T4 quote 追问 = 穷人版多轮 ★ 惊喜发现

**做什么**：用户**引用机器人上一条答案**追问时，协议把被引全文送回来——handler 把它拼进 prompt（「上一轮答案：…；追问：…」），即获得最常见的多轮场景（追问/让它展开/纠偏），**不需要任何会话存储**。

**为什么**：P2 的完整 history（会话键+TTL+query 改写）是大工程；quote 版本成本低一个量级，先吃掉 80% 追问场景，还天然精准（用户明确指定了上下文）。

**成本**：低。handler + answer prompt 拼装，加一段文档教用户「引用回答可追问」。

### T5 企微收件箱：单聊传文件入库（供给侧闭环）

**做什么**：用户单聊把 PDF/文档拖给机器人 → tunnel 下载（url+aeskey AES 解密）→ 灌 veda 既有 blob+PDF 抽取管线 → 回「已入库」卡片。语音提问顺手支持（官方转写文本直接当 query，几乎零成本）。

**价值**：问答是消费侧，这是**供给侧**——知识库更新不用开 console。
**卡点（先设计再做）**：bot 的 wk_ 是只读的——投喂需要写权限 + **谁可以投喂**的授权模型（per-bot 维护者 userid 白名单是最简解）。乱投喂会污染知识库，安全模型不定不动手。

**成本**：中（下载解密 + 白名单 + 写路径切换 readwrite key）。

### T6 主动推送：更新订阅 / 异步交付

**做什么**：① tunnel 记 reachable 会话表（首次收消息 upsert chattype+chatid/userid）——**这张表建议尽早开始积累**（零成本，解锁未来一切推送场景）；② 场景按需上：知识库文档变更通知（veda `/v1/events` SSE 变更流现成，tunnel 订阅→推送）、群定期摘要、超长查询「稍后送达」（response_url 1h 补发）。

**为什么排后**：推送是打扰型能力，需求未经 DAL 用户验证；但 reachable 表的积累是时间函数，先埋。

**成本**：表+upsert 极低；订阅推送中。

### T7 答案富格式与引用可点

- 答案里的表格/代码块：markdown-v2 已支持，检查 render 路径是否透传（低成本确认项）
- **引用可点**：citations 的 path 变成 console 文件页 deep-link（刚上的 `#/console/fs/{ws}` 有了骨架，缺 path 定位/预览锚点；且链接需要收信人有权限——console 要 vk/wk，链接落地页的鉴权体验要设计）
- finish 帧带图：依赖图片内容索引（evidence-gated，等 OCR 方向有结论）

**成本**：确认项低；deep-link 中。

### T8 欢迎语（enter_chat）

当天首次进单聊 → 欢迎卡片：「我接的是 XX 知识库，试试问：…（示例问题）」。示例问题可以从 qa_log 的高频 query 生成（依赖 T1）。**成本极低，体验细节**。

### T9 多实例 HA（选主）

单点 .95：进程崩了 systemd 拉起（秒级），但机器挂了企微就断服直到人工恢复。方案在案（MySQL `GET_LOCK` 选主，drive9 对标结论）。**当前接受单点**（与 veda-server 同一取舍，deploy.md 已明示）；用户量上来或出过一次真实事故再做。

### 边缘（记录在案，不主动做）

- 飞书/钉钉 adapter：架构留了位（`wecom/` 平级），公司主战场是企微，无需求不做
- 一 bot 多知识库路由：改变「一 bot 一库」心智模型，需求未出现
- 完整多轮 history（P2 维持）：T4 quote 版先行，等它不够用的证据

### 明确不做（协议证伪）

答错撤回、进群自动自我介绍、按用户名/群名个性化、群聊收文件。

## 建议打包

| 波次 | 内容 | 逻辑 |
|---|---|---|
| **第一波** | T1 质量遥测 + T2 流式 + T4 quote 追问 + T8 欢迎语（+T6 的 reachable 表先埋） | 度量地基 + 最大体感 + 两个低成本高杠杆 |
| **第二波** | T3 OTLP 告警 + T7 引用可点 | 运维底座 + 体验补全 |
| **验证后** | T4→T5 收件箱与推送（安全模型/需求验证通过后） | 供给侧与通知面 |
| **事件驱动** | T9 HA | 出事故或用户量拐点 |
